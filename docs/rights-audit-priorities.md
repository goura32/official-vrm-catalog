### 個別監査で分離する判断軸

1. **出典と権原**：制作者/正規配布先か、第三者素材・モデルの許諾根拠は何か。
2. **入手行為**：無料で正規に入手可能か。利用規約への同意、アカウント権限、レート制限を尊重。既存holdの無差別な再取得をしない。
3. **複製の根拠**：明示ライセンスだけではなく、日本の著作権法第30条（私的使用）・第30条の4（非享受目的）が**対象・利用目的・必要な範囲・例外要件**に適用されるかを個別検討。条文上の例外が適用されるなら「独立した長期保存の明示許諾がない」ことだけで自動的に複製禁止にはしない。ただし、例外の適用を無条件に推定せず、取得サイトの利用規約・契約上の制限・違法な取得や権利者の不当な利益侵害の可能性も区別する。
4. **利用行為**：VRMの`OnlyAuthor`、商用不可、`Redistribution_Prohibited`等は、アバター利用・商用・再配布に関する条件。**この条件だけで非公開技術検査用の私的複製が禁止とは断定しない**。条件同士が食い違う事実は消さない。
5. **モデル固有の一致**：作者名、配布ファイル、実VRMメタデータ、ID/版、形状、第三者権利。共通ライセンス表示を無条件に全構成要素へ適用しない。
6. **保存先の隔離**：現状のNFS設定では非公開性が未確定。仮に技術検査用複製の根拠が明確でも、NASへの**新規保存は隔離確認まで停止**。既存487 ZIP/974 WebPは変更せず保護する。

## NAS管理者側での読み取り専用確認

B84時点のクライアント観測：`/mnt/hdd/vrm`とmodels/previews等のディレクトリが`0777`、索引`index.jsonl`は`0600`、`.index.lock`は`000`、確認したnamed/default ACLなし。NFSv3 `sec=sys`、エクスポート許可はプライベートIPv4 `/24`。**これは特定のLAN内だけに接続先を限定する情報であり、個々の利用者の隔離が証明されたわけではない。** `0777`ディレクトリでは`0600`ファイルの削除・移動等の保護も不十分になり得る。NFSのAUTH_SYSは基本的にクライアントのUID/GID申告を使うため、クライアント自体の信頼性が重要。

NAS管理者が**NAS本体で**次の項目を読み取り専用で照合する。情報の採取は管理者の許可範囲に限定し、パスワード・認証鍵や全exportsをGitに載せない。

```bash
sudo exportfs -v
sudo stat -c '%a %U:%G %n' /volume1/hdd/vrm /volume1/hdd/vrm/models /volume1/hdd/vrm/previews /volume1/hdd/vrm/index.jsonl
sudo getfacl -p /volume1/hdd/vrm /volume1/hdd/vrm/models /volume1/hdd/vrm/previews /volume1/hdd/vrm/index.jsonl
```

確認事項：実際にどのホストがマウントできるか、サーバー側NFS exportの`root_squash`/`all_squash`/`anonuid`/`anongid`/UID-GID対応、サーバー側ACL・共有ポリシー、全親ディレクトリの所有者と実効書込み権限、NAS内の他サービス経由アクセス、スナップショット/バックアップや他ユーザーからの可視性。NAS実パスが異なるときは**実際のエクスポートパス**に読み替える。

仮に権限を`0700`へ変更しても、許可された別クライアントがUIDを詐称できる`AUTH_SYS`環境では、それだけで隔離を証明できない。許可ホストを本当に信頼できる端末へ限定し、サーバー側のUID/アクセス制御と必要なら暗号化・認証方式を含めて評価する。NASアプリや既存データの所有権を壊さないよう、変更は**別途管理者の承認と復旧手順を確認した後のみ**行う。
